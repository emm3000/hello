# Flashcard Generation Action Plan

## Objective

Redesign the flashcard generation flow so the app creates high-value Anki-style study material that genuinely helps users learn English through:

- active retrieval
- spaced repetition
- minimal-information cards
- meaningful context
- productive recall, not only passive recognition

This plan is intentionally staged for trial-and-error development. During experimentation, local database and Supabase schema may be changed directly without formal migrations if needed. However, every schema change must be reflected consistently in models, queries, parsers, sync payloads, and UI contracts.

## Product Direction

The target is not "one rich flashcard with too much text". The target is:

1. one rich learning note
2. multiple simple cards derived from that note

The note stores linguistic value and teaching context. The cards store retrieval tasks.

Recommended derived cards per note:

- Recognition card: `EN -> ES`
- Production card: `ES/context -> EN`
- Cloze card: sentence with one hidden target
- Form card: only when relevant, for example irregular verb forms, required prepositions, or phrasal verb behavior

## Evidence-Informed Principles

These principles should drive every decision in the generation flow:

- Retrieval practice matters more than passive rereading.
- Distributed practice is a high-utility learning technique.
- Cards should respect the minimum-information principle.
- One note can generate multiple cards if each card tests one thing clearly.
- Context improves usefulness, but the retrieval task should remain simple.
- Productive recall should be part of the system, not only recognition.

References:

- Roediger & Karpicke, test-enhanced learning: https://pubmed.ncbi.nlm.nih.gov/16507066/
- Karpicke & Roediger, repeated retrieval and feedback: https://pubmed.ncbi.nlm.nih.gov/19966244/
- Dunlosky et al., effective learning techniques: https://pubmed.ncbi.nlm.nih.gov/26173288/
- SuperMemo 20 rules: https://super-memory.com/articles/20rules.htm
- Anki note/card model and templates: https://docs.ankiweb.net/templates/intro.html
- Anki cloze and typed answer support: https://docs.ankiweb.net/templates/fields.html?highlight=type+answer

## Current Problems To Solve

- The current flow is centered on `1 input -> 1 flashcard`.
- Study mode mainly trains recognition, not production.
- The generation prompt asks for rich data, but not all of it survives to persistence and review.
- The app accepts weak or ambiguous input.
- Category-based generation is not aligned with communicative intent.
- Quality is delegated too heavily to the prompt.
- There is no quality gate before saving.
- The preview is not editable.

## Scope Boundaries

This initiative should refactor the flashcard generation contract, not the entire app.

In scope:

- input model
- generated note schema
- derived card schema
- prompt redesign
- preview redesign
- quality validation
- review type support
- database/model/query alignment

Out of scope for the first pass:

- full pedagogy analytics dashboard
- advanced personalization engine
- adaptive curriculum sequencing across multiple skills

## Architecture Target

### Core Concept Shift

Replace:

- `FlashcardGenerated`

With something closer to:

- `GeneratedLearningNote`
- `GeneratedCard`

### Suggested Note Fields

The generated note should contain:

- `expression`
- `lemma`
- `intendedMeaningEs`
- `simpleDefinitionEn`
- `partOfSpeech`
- `type`
- `ipa`
- `register`
- `level`
- `domain`
- `usagePattern`
- `irregularForms`
- `collocations`
- `commonMistake`
- `confusableWith`
- `exampleSentence`
- `exampleTranslation`
- `clozeSentence`
- `whyUseful`
- `qualityChecks`
- `cards`

### Suggested Derived Card Types

- `recognition`
- `production`
- `cloze`
- `form`

Each derived card should have a single retrieval target.

## Data and Schema Rule During Experimentation

Formal migrations are not required for this phase, but schema changes are never isolated.

Every database change must update all of the following, if applicable:

- SQLDelight schema
- local entity/domain models
- DTOs and parsers
- repository write paths
- repository read paths
- sync payloads
- Supabase table structure
- Supabase RPC or sync logic
- UI state and preview models

If a field is generated by AI but is not persisted or reviewed, that field should be either:

- fully integrated, or
- removed from the contract until it is truly used

## Phases

## Phase 0: Define The Learning Contract

### Goal

Lock the product decision that the system generates learning notes plus derived cards, not just single front/back flashcards.

### Atomic Tasks

- Create the canonical list of note fields.
- Create the canonical list of derived card types.
- Define which note fields are mandatory by word type.
- Define which card types are generated for each note type.
- Define what "saveable quality" means.
- Document banned note patterns.

### Banned Patterns

- one note with multiple meanings
- vague translation without intended sense
- examples with unnatural English
- examples with too many unknown words
- overloaded back sides
- generated tags or forms that are never used

### Exit Criteria

- The team has one source of truth for note schema.
- The team has one source of truth for card types.
- There is a written quality gate.

## Phase 1: Redesign User Input

### Goal

Stop accepting weak input that leads to weak cards.

### Input Strategy

Replace the current minimal input with a guided input contract.

### Required Inputs

- `inputType`
- `userText`
- `goal`
- `level`

### Conditionally Required Inputs

- `intendedMeaningEs` when the term is ambiguous
- `contextSentence` for polysemous words or phrases
- `register` when tone matters
- `domain` when use-case matters

### Recommended Input Types

- `word`
- `phrase`
- `sentence`
- `communicative_goal`

### Better Category Replacement

Replace broad grammar-style categories with communicative intents such as:

- order food
- describe past events
- make polite requests
- complain
- express uncertainty
- talk about plans

### Atomic Tasks

- Add a source-of-truth enum for input types.
- Add a source-of-truth enum for learning goals.
- Add a source-of-truth enum for level values.
- Add ambiguity rules that force extra context.
- Remove or de-prioritize weak static categories.
- Define validation messages for ambiguous inputs.
- Define UI copy that does not conflict with supported languages.

### Exit Criteria

- A user cannot submit low-information ambiguous input without guidance.
- Input values map cleanly to prompt fields.

## Phase 2: Redesign AI Output Contract

### Goal

Make AI return a durable, reviewable learning note with derived cards.

### Output Strategy

The model should return a structured note, not a pretty answer blob.

### Atomic Tasks

- Create `GeneratedLearningNote` domain model.
- Create `GeneratedCard` domain model.
- Define `qualityChecks` structure in the output.
- Define `warnings` structure in the output.
- Define per-note-type required fields.
- Define per-card-type required fields.
- Define stable enums for card type, register, and note type.
- Remove fields from the contract that are not yet used.

### Minimum Output Expectations

- exactly one intended sense per note
- one strong example sentence
- one cloze sentence if the note type supports it
- one production prompt if the goal is production or both
- verb forms only when relevant
- usage pattern only when relevant

### Exit Criteria

- AI output can be persisted without ad hoc interpretation.
- All generated fields have a clear product use.

## Phase 3: Rewrite The Prompt System

### Goal

Use prompts to populate a strong contract, not to compensate for weak product design.

### Prompt Principles

- Ask for one intended meaning only.
- Ask for natural, high-frequency, level-appropriate language.
- Ask for communicative usefulness.
- Ask for context realism.
- Ask for split notes when meanings diverge.
- Ask for cards derived from the note.
- Ask for warnings when the input is under-specified.

### Atomic Tasks

- Remove artificial randomness constraints from generation.
- Replace broad category prompts with communicative-intent prompts.
- Split prompts by input type where necessary.
- Add prompt sections for ambiguity handling.
- Add prompt sections for productive recall generation.
- Add negative examples of bad cards.
- Add positive examples of strong notes and strong derived cards.
- Standardize output schema across all generation modes.

### Exit Criteria

- Prompt output aligns one-to-one with the note contract.
- Prompt no longer invents fields the app ignores.

## Phase 4: Build A Quality Gate Before Save

### Goal

Prevent low-value notes from entering the deck.

### Quality Rules

A note should fail save if:

- the intended meaning is unclear
- the example is unnatural or too generic
- the production answer is ambiguous
- the note mixes multiple senses
- the example sentence overloads the learner
- required fields for the word type are missing

### Atomic Tasks

- Implement a local validation layer for generated notes.
- Add validation for single-sense notes.
- Add validation for example complexity.
- Add validation for minimum required fields per note type.
- Add validation for card answer uniqueness.
- Add validation for productive card ambiguity.
- Add warnings for low-confidence notes.
- Block save on hard failures.
- Allow save with warnings only when acceptable.

### Exit Criteria

- The app rejects obviously poor notes before persistence.
- Users see why a note is blocked or warned.

## Phase 5: Redesign Preview And Editing

### Goal

Make the preview a real review surface, not just a final confirmation.

### Preview Requirements

The user must be able to inspect and edit:

- intended meaning
- translation
- definition
- example sentence
- cloze sentence
- usage pattern
- common mistake
- derived cards

### Atomic Tasks

- Replace read-only preview with editable note preview.
- Add editable sections per note field.
- Add per-card preview tabs or sections.
- Show card type labels clearly.
- Show validation warnings inline.
- Allow regenerate single field, not whole note only.
- Allow regenerate example only.
- Allow regenerate production card only.

### Exit Criteria

- Users can fix a mostly-good note without starting over.
- Users can inspect exactly what will be studied.

## Phase 6: Expand Study Mode Beyond Recognition

### Goal

Make review sessions train both comprehension and production.

### Study Strategy

Support multiple retrieval tasks:

- recognition
- production
- cloze
- form recall

### Atomic Tasks

- Extend study model to support card subtypes.
- Add rendering rules per card subtype.
- Add typed-answer UI for production cards.
- Add cloze UI for sentence cards.
- Add form-specific UI for verbs and phrasal verbs.
- Ensure scheduler works with the new card subtypes.
- Decide whether siblings are buried or shown together.

### Exit Criteria

- The same note can train more than passive recognition.
- Study mode reflects the actual intended learning outcome.

## Phase 7: Align Persistence, Local DB, And Supabase

### Goal

Keep the experiment stable while schema changes rapidly.

### Atomic Tasks

- Update local database tables for note/card structure.
- Update SQLDelight queries for reads and writes.
- Update domain models.
- Update repository mapping logic.
- Update sync payload structures.
- Update Supabase schema directly if needed.
- Update Supabase sync logic and RPC assumptions.
- Remove obsolete columns and dead code paths when replaced.
- Verify round-trip persistence for every new field.

### Safety Rule

Never leave a partially integrated field in only one layer.

### Exit Criteria

- Every persisted field survives create, fetch, sync, and review.
- No ghost fields remain in prompts only.

## Phase 8: Evaluation Loop

### Goal

Move from intuition to measured quality.

### Evaluation Method

Create a small internal benchmark of generated notes and score them.

### Suggested Rubric

- single clear meaning
- naturalness
- usefulness in real communication
- level fit
- production suitability
- cloze suitability
- example quality
- ambiguity risk

### Atomic Tasks

- Create a 25 to 50 input benchmark set.
- Include ambiguous words, phrases, verbs, phrasal verbs, and intents.
- Score outputs with a rubric.
- Track failure modes.
- Refine prompts and validation from observed failures.
- Re-run benchmark after each major generation change.

### Exit Criteria

- Generation quality is measured, not guessed.
- Prompt changes are evaluated against a stable benchmark.

## Implementation Order Recommendation

Recommended order:

1. Phase 0
2. Phase 1
3. Phase 2
4. Phase 3
5. Phase 4
6. Phase 5
7. Phase 7
8. Phase 6
9. Phase 8

Reasoning:

- Input and schema must be correct before prompt tuning.
- Prompt tuning must happen before strict validation.
- Persistence must follow the new contract before the new study mode depends on it.

## Immediate First Sprint

If this is started now, the first sprint should focus only on:

- locking the new note schema
- locking the card subtype schema
- replacing category generation with communicative intent
- rewriting the prompt contract
- implementing validation for ambiguous input
- building editable preview for core fields

Do not start by polishing UI or adding more examples. The structural contract comes first.

## Definition Of Success

This initiative succeeds when:

- the user can give clear intent
- the AI returns a structured, useful note
- the app blocks weak notes
- the app saves only integrated fields
- the user studies both recognition and production
- the resulting cards are simple, answerable, and reusable in spaced repetition

## Final Product Standard

The final standard is:

- rich note
- simple cards
- clear meaning
- natural context
- productive recall support
- no wasted generated fields
- no hidden schema drift

That is the direction most likely to produce flashcards that truly help users learn, instead of only looking complete in preview.
